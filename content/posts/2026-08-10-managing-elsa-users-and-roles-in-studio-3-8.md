# Managing Elsa Users and Roles in Studio 3.8

Elsa has long exposed APIs for managing its built-in users and roles. The awkward part was the operator experience: routine identity administration still meant calling those APIs directly or building a separate screen around them.

[Elsa Studio PR #936](https://github.com/elsa-workflows/elsa-studio/pull/936) closes that gap for the 3.8 line. Studio now provides permission-aware lists and editors for users and roles under **Administration > Identity & access**. The same work covers both Blazor Server and WebAssembly hosts, generated-password handling, role assignment, permission editing, and destructive-action confirmation.

> **Key Takeaways**
> - Studio shows identity pages and actions only when the connected server exposes the feature and the signed-in user has the matching permission.
> - Server-side authorization remains the security boundary, including checks that prevent an administrator from assigning permissions they do not hold.
> - A password can be supplied during user creation or generated by the server and shown once by Studio.

> **Availability:** User and role management merged into `release/3.8.0` on August 4, 2026. The latest stable Elsa release is 3.7.1, and `3.8.0-preview1` predates this work. Use a post-merge 3.8 preview that includes Studio #936, and keep the Studio, API client, and server packages aligned. The server-host configuration safeguard described below requires [Studio PR #937](https://github.com/elsa-workflows/elsa-studio/pull/937), merged August 8. [Elsa 3.8 Preview 1](/blog/elsa-3-8-preview-1) provides broader release context.

This post is about Elsa's own identity records and permissions. If your Studio host signs users in through an external provider, start with [OpenID Connect in Elsa Studio](/blog/openid-connect-in-elsa-studio) to understand that separate authentication boundary.

## What did Studio add?

Studio 3.8 adds two identity-management lists and two shared create/edit page components. The implementation calls the existing `/identity/users` and `/identity/roles` endpoints through narrow API clients instead of introducing a second administration contract.

The practical result is a familiar resource-management flow:

- list and locally filter users or roles;
- create a user and select roles;
- change a user's password or role assignments;
- create and edit roles with explicit permission tokens;
- confirm user or role deletion before Studio sends it.

The [feature design](https://github.com/elsa-workflows/elsa-studio/blob/51a954e219d5abdef24eeeab271a61aa87282807/specs/012-user-role-management/design.md) explains two details that keep the first version honest. User names are immutable after creation because the server update contract changes only passwords and roles. Lists filter locally because the current server endpoints return complete collections without paging or search. Studio does not pretend those capabilities exist.

The PR's verification reports 20 focused administration tests, clean Server and WebAssembly host builds, and browser-tested user and role flows. The test coverage includes routes, menu gates, payloads, generated-password disclosure, deletion confirmation, and stale asynchronous operations.

That last case matters in a Blazor administration screen. If an operator navigates from one record to another while a request is still completing, an old response must not overwrite the new editor. The pages version their loads and ignore stale completions before changing visible state.

## How does permission-aware navigation work?

Studio checks two signals before adding **Users** or **Roles** to the Identity & access menu. The connected server must report the remote Identity feature, and the current principal must hold `read:user` or `read:role`. A wildcard `*` permission satisfies both checks.

The editor actions then use the matching operation permissions:

| Resource | Read | Create | Update | Delete |
| --- | --- | --- | --- | --- |
| User | `read:user` | `create:user` | `update:user` | `delete:user` |
| Role | `read:role` | `create:role` | `update:role` | `delete:role` |

The [menu contributor](https://github.com/elsa-workflows/elsa-studio/blob/51a954e219d5abdef24eeeab271a61aa87282807/src/modules/Elsa.Studio.Security/Menu/IdentitySecurityMenuContributor.cs) hides resources the user cannot read. The list and editor pages separately gate create, save, and delete controls. A user editor also needs `read:role` before it can load the available roles for assignment.

<!-- [UNIQUE INSIGHT] -->

Hidden controls improve clarity, but they are not the authorization boundary. Every Core endpoint declares its own permission requirement. The [user endpoints](https://github.com/elsa-workflows/elsa-core/tree/5429008d98a56afd29b4fd11107f7760710b1a64/src/modules/Elsa.Identity/Endpoints/Users) enforce the four user permissions, and the [role endpoints](https://github.com/elsa-workflows/elsa-core/tree/5429008d98a56afd29b4fd11107f7760710b1a64/src/modules/Elsa.Identity/Endpoints/Roles) do the same for roles. A handcrafted request cannot bypass those server checks just because Studio would have hidden the button.

## What prevents privilege escalation?

Endpoint permissions answer whether a caller may perform an operation. Elsa also checks what the requested operation contains. The [role authorization service](https://github.com/elsa-workflows/elsa-core/blob/5429008d98a56afd29b4fd11107f7760710b1a64/src/modules/Elsa.Identity/Services/RoleAuthorizationService.cs) requires the caller to hold every permission carried by a role they assign, create, or mutate, unless the caller has the wildcard permission.

That produces an important distinction:

- `create:user` lets an administrator create a user, but not grant that user a role with permissions the administrator does not have.
- `update:role` lets an administrator edit a role, but not preserve or add permissions outside their own grant set.
- creating a role also passes the server's `SecurityRoot` policy in the current Core implementation.

Studio sends role IDs when it creates or updates users. Core resolves those IDs, rejects unknown roles, collects their permissions, and compares the result with the caller's permission claims. The server therefore protects the boundary even if a client submits a role that was not offered by the UI.

This is the useful mental model: operation permissions control the verb; role-content checks control the authority being delegated.

## How are passwords handled?

When creating a user, Studio accepts an explicit password or leaves the field empty. An empty value asks the server to generate a password. Studio displays the returned value in a dedicated dialog that says it will be shown once, then navigates to the new user's editor.

The [user editor](https://github.com/elsa-workflows/elsa-studio/blob/51a954e219d5abdef24eeeab271a61aa87282807/src/modules/Elsa.Studio.Security/Pages/User.razor.cs) clears password fields after a successful update. Its local response models deserialize only the fields the UI needs, so older server responses containing password hashes do not become Studio state. On an existing user, leaving the password blank means "leave unchanged."

There is still an operator responsibility here. A generated password is a one-time handoff secret. Copy it directly into the approved delivery channel or password manager. Do not put it in a ticket, log, screenshot, or workflow definition.

For other sensitive values used by workflows, [secret references in Elsa 3.8](/blog/secret-references-in-elsa-3-8) cover the separate design for keeping secret material out of definitions.

## Why are role permissions edited as tokens?

The role editor uses an explicit add/remove token field because the server does not currently expose a permission-catalog endpoint. A hard-coded checklist in Studio would look friendlier, but it could become incomplete as modules contribute new permissions.

That choice keeps the server authoritative and makes custom module permissions usable immediately. It also means operators need the exact permission strings supplied by the module they are configuring. The built-in identity permissions in the table above are examples; they are not the complete Elsa permission vocabulary.

The safer workflow is to create narrow roles around a real job, add only known permission tokens, and verify the resulting account before broadening it. Avoid `*` for routine administration. It is intentionally a universal grant, not a shorthand for "most things."

Deletion is conservative too. Studio asks for confirmation and surfaces conflict responses instead of pretending a blocked role was removed. Core has richer role-dependency inspection and remediation endpoints, but the initial Studio UI deliberately leaves that advanced workflow out of scope.

## How do local authentication overrides stay out of source control?

The Server host now loads an optional `appsettings.Local.json` after the tracked settings. [Studio PR #937](https://github.com/elsa-workflows/elsa-studio/pull/937) also git-ignores that file, so a developer can switch authentication providers, change the backend URL, or supply a local client secret without editing committed configuration.

For example, a local external-authentication setup can live in:

```json
{
  "Authentication": {
    "Provider": "ExternalAuthentication",
    "ExternalAuthentication": {
      "ClientSecret": "local-development-secret"
    }
  }
}
```

The shipped Server host continues to default to `ElsaIdentity` with an empty external-authentication client secret. That keeps a fresh checkout runnable while giving each developer an untracked override layer.

Do not mistake git-ignore for production secret management. `appsettings.Local.json` is a development convenience. Production client secrets still belong in environment-specific configuration or a managed secret store.

## Frequently asked questions

### Does Studio authorization replace the server's endpoint checks?

No. Studio uses feature and permission claims to show the correct navigation and actions, but Core authorizes every identity request again. The server also validates assigned role IDs and prevents callers from delegating permissions they do not hold, regardless of which client sends the request.

### Can an administrator change a user's name?

No. The current API treats the user name as immutable after creation. Studio therefore displays it as read-only on the edit page. Administrators can change the password and role assignments. If the identity name must change, create a replacement account and migrate its grants deliberately.

### Does this require Elsa Identity as Studio's login provider?

The managed records come from the connected server's Elsa Identity feature. Studio itself can authenticate through Elsa Identity or another configured provider, provided the resulting backend token carries the required Elsa permission claims. Authentication decides who signed in; these pages administer Elsa's user and role resources.

### Why don't I see Users or Roles in the menu?

First confirm that the connected server exposes the Identity feature. Then inspect the signed-in user's permission claims: the menu requires `read:user` for Users and `read:role` for Roles. Finally, confirm that Studio and the server come from aligned post-merge 3.8 preview builds.

## The practical takeaway

User and role management in Studio turns an existing API surface into an operator-facing workflow without weakening the boundary behind it. Navigation stays capability-aware, actions stay permission-aware, and Core still validates both the requested operation and the authority being delegated.

The best place to start is a narrow test role. Give it only the read permission for the resource it needs, sign in as a test user, and confirm Studio's menu and actions match that grant. Add create, update, or delete permissions only when the job actually requires them.
